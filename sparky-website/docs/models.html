Models and providers

Connect the provider you choose, then let Sparky display the models, context limits, and reasoning controls that provider actually reports.

The model picker is live, not a fixed website catalog. Providers can add, remove, rename, or restrict models independently of a Sparky release. Settings in the installed app are the source of truth for what your account can use now.

Provider connections

Add a provider in Settings, Models. The credential or account connection must belong to the provider you select, and the available catalog can depend on that account's access.

How discovery works

Sparky reads capability metadata from the provider instead of assigning the same controls to every model. Version 1.1.2 supports nested and alternate metadata shapes, plain numeric context limits, and values written with k or m suffixes. Anthropic and Google detail endpoints can enrich the base response, and Models.dev metadata can act as a fallback when primary information is incomplete.

The app also reduces duplicate entries and does not invent unsupported reasoning levels. This is why two models from the same provider can show different controls, and why a website list would become stale.

Context and reasoning controls

  • Context window describes how much provider input a model can accept. It is discovered when reliable metadata is available.
  • Reasoning effort appears only when the provider reports supported levels for that model.
  • Image support remains a provider and model capability. Attaching an image does not make a text-only model multimodal.
  • User settings remain authoritative where Sparky explicitly allows an override, including an explicit context setting.

Do not choose a model by context size alone. Match the model to the task's complexity, required tools, image needs, latency tolerance, and account cost controls.

Codex OAuth sessions

Codex OAuth connections have provider-thread continuity and native /compact handling in Sparky 1.1.2. When a supported conversation exceeds its context window, Sparky can compact the same provider thread and retry once. Per-model limits are used when available, and oversized reported limits are handled conservatively.

Provider continuation state is stored with the session. If required resume state is missing, Sparky should report the problem instead of silently replacing the conversation.

Switching models

Open Settings, Models, select a configured provider, and choose from its discovered catalog. A model change affects later provider requests; it does not rewrite earlier assistant messages or convert provider-specific continuation data into another provider's format.

For continuity-sensitive work: Finish or summarize a provider-specific line of reasoning before switching providers. Provider-specific opaque state is intentionally kept out of unrelated provider formats.

Refresh and configuration changes

Relevant provider or MCP configuration changes trigger reloads of the affected catalog data. MCP launch arguments can be detected from static and dynamically resolved sources. If the picker looks stale, confirm the credential and configuration first, then reopen the relevant settings rather than relying on a model name copied from this website.

If an option is missing

  1. Confirm that the intended provider is configured and authenticated.
  2. Check that the account has access to the model.
  3. Remember that unsupported reasoning levels are deliberately omitted.
  4. Refresh after a provider or MCP configuration change.
  5. If an image is rejected, confirm that the selected model supports multimodal requests.
  6. Capture the visible provider, model, and error state when reporting a discovery problem.
