What's new in Sparky 1.1.2

A complete guide to the latest Sparky desktop app across Windows, macOS, and Linux: Memory, continuous conversations, provider-aware models, image prompts, Plan mode, tools, notifications, web search, and browser preview.

One app, platform-specific packages: The features below describe Sparky 1.1.2 as a whole. Windows, macOS, and Linux use different installers, but they share the desktop workspace, local server, Rust agent harness, provider integrations, and project tools. See the download page for the package offered to your platform.

Release and platform packages

Sparky 1.1.2 is a local desktop coding workspace. Its user interface, local coordination server, and Rust agent runtime are packaged together so the normal app does not require you to assemble a development environment.

What the desktop app includes

Every platform package is more than a shortcut to a hosted website. It contains the desktop workspace and local runtime used to operate on projects on your machine.

  • The Sparky desktop shell. This is the native desktop window, menus, settings, update integration, notifications, project selection, and desktop IPC layer.
  • The complete Sparky web interface. The thread view, composer, settings screens, model picker, Memory manager, tool timeline, file views, Diff view, terminal surface, and browser preview UI are bundled with the application.
  • The local Sparky server. The packaged server coordinates projects, sessions, provider connections, attachments, terminal work, browser preview requests, and communication between the UI and the agent runtime.
  • The embedded Rust agent harness. The platform package includes the Sparky executable used for Build mode, Plan mode, provider requests, Memory tools, file tools, and structured tool execution.
  • Required runtime dependencies. The package contains the application dependencies and native modules required by the desktop and local-server paths rather than asking the user to assemble a development environment.
  • Brand and application resources. The current Sparky logo, platform application icons, splash resources, and product metadata are included in the installed application.

Persistent Memory

Memory is the largest new user-facing capability in 1.1.2. It gives Sparky an explicit, manageable place to retain information that should be available beyond one message or one conversation.

Create and manage memories

  • Create a memory from the Memory area in Settings.
  • Search saved memories instead of manually scanning old conversations.
  • Edit a memory when a convention or preference changes.
  • Delete information that Sparky should no longer reuse.
  • Assign categories and importance levels so saved context can be organized and prioritized.

Choose the scope

  • Global memories are available across projects. They are suitable for preferences such as how you want results summarized or how cautiously Sparky should handle unrelated changes.
  • Project memories are tied to one workspace. They are suitable for repository conventions, commands, architectural decisions, required tests, or project-specific terminology.

How Memory behaves

  • Saved memories can be reused in future conversations and later application sessions.
  • Memory locations resolve across supported desktop platforms.
  • Existing memory locations have migration and recovery handling.
  • Duplicate entries with the same memory ID are merged instead of appearing as independent conflicting copies.
  • Loading, retrying, saving, updating, and deleting each expose their own error state.
  • A Memory failure is contained so it does not crash the surrounding conversation.
  • The same Memory system is available to the Rust tool layer and the web-based Settings interface.

Conversation continuity and long sessions

Sparky 1.1.2 keeps more than the visible chat transcript. It also persists the provider continuation state required to resume the same underlying provider conversation.

  • Follow-up messages continue the existing provider conversation instead of silently creating a new hidden session.
  • Provider bindings and transcripts are stored under Sparky's session directories and survive an application restart.
  • Opaque continuation data is preserved with assistant messages without being exposed as ordinary chat text.
  • Two-turn recall survives session reload and context compaction.
  • GPT-5.6 encrypted reasoning items are retained and replayed in the provider format that expects them.
  • Provider-specific continuation state is isolated from unrelated provider formats.
  • If required resume state is missing, Sparky reports the failure instead of silently starting an unrelated fresh conversation.
  • Incomplete provider streams are not marked as successful completed turns.
  • A turn is considered complete only after a valid user-facing summary is available.
  • The previous premature round cutoff was removed so longer coding tasks are not terminated solely because they crossed that fixed internal limit.

Codex OAuth and context compaction

Codex OAuth sessions receive native context-management behavior in this release.

  • The /compact operation compacts the active Codex OAuth conversation while preserving its provider-thread identity.
  • When the context window overflows, Sparky compacts that same provider thread and retries once rather than discarding the conversation.
  • OAuth context limits are handled conservatively so an oversized or unreliable reported limit is not trusted blindly.
  • Per-model context limits are used when the provider supplies them.
  • An explicit context setting supplied by the user remains authoritative.
  • Compaction lifecycle events settle correctly so the interface does not remain stuck in a busy state.
  • GPT-5.6 continuation data survives follow-up messages, reloads, and compaction.

Provider and model capabilities

The model picker is driven by provider data rather than a fabricated one-size-fits-all capability list.

  • Reasoning-effort options are discovered from provider metadata.
  • Context-window sizes are discovered from provider metadata.
  • Capability parsing supports nested fields, alternate field names, raw numbers, and values expressed with k or m suffixes.
  • Anthropic and Google model-detail endpoints can enrich the base catalog.
  • Models.dev metadata can supply a fallback when primary metadata is incomplete.
  • The UI does not invent unsupported reasoning levels.
  • Disabled OpenCode variants are filtered from the list.
  • Duplicate model-picker entries are reduced.
  • Provider configuration changes reload the relevant model and MCP catalog data.
  • MCP launch arguments can be detected from static and dynamically resolved sources.
  • A new thread still receives a title derived from its first user message.

Because this information is provider-authoritative, the exact models and reasoning levels visible in your installation can change when your provider changes its catalog. See Supported Models for usage guidance.

Image and multimodal prompts

Sparky 1.1.2 can carry image attachments through the desktop, local server, and Rust request path instead of treating them as UI-only metadata.

  • Attach screenshots, UI references, diagrams, and other supported images to a prompt.
  • Uploaded files resolve through Sparky's managed attachment directory.
  • Files are validated before they are sent to a provider.
  • Images are encoded as base64 multimodal request parts with their MIME type.
  • An image-only message receives an effective textual prompt so it is not discarded as an empty request.
  • Normal conversations use Sparky Build mode unless the user explicitly selects another interaction mode.

Rust-native Plan mode

Plan mode is implemented inside Sparky's Rust harness and is intentionally separated from Build mode.

  • Plan requests use --interaction-mode plan.
  • A dedicated planning prompt tells the agent to investigate, reason about the task, and produce an actionable approach before implementation.
  • The planning tool policy is read-only so selecting Plan does not quietly edit project files.
  • ask_user is available when a material decision genuinely requires the user's answer.
  • update_plan records the structured task plan.
  • Switching back to Build mode restores normal implementation tools.
  • Generic Plan mode is not secretly routed to OpenCode's separate native plan agent.

Tool execution, file editing, and timeline states

Sparky 1.1.2 includes the updated tool protocol and its corresponding presentation in the desktop timeline.

  • Windows and CRLF-formatted files receive safer edit handling.
  • Stale-file detection notices when the working copy no longer matches the snapshot an edit was prepared against.
  • Sequential edits use current file snapshots so one edit is less likely to invalidate the next.
  • Ambiguous replacement matches produce a clear failure instead of changing an arbitrary occurrence.
  • Malformed and incomplete tool arguments receive more defensive handling and recovery guidance.
  • Large or truncated tool-call payloads are handled more carefully.
  • File-change statistics can update while work is still running.
  • Tool results distinguish Running, Completed, Failed, Stopped, and Declined.
  • Built-in tools use distinct inline icons, and web search has its own lifecycle type.
  • Workspace scanning is shared by context-file and skill discovery instead of duplicating the same inventory work.
  • Context summaries and recent-history tails are bounded before they are inserted into later requests.

Streaming appearance and response controls

Streaming behavior

  • Provider text deltas are published immediately while nearby deltas are grouped into short rendering windows.
  • Growing Markdown is paced at roughly 48 milliseconds instead of reparsing the entire response for every tiny delta.
  • Previously rendered assistant text stays stable while new text arrives.
  • Only the current turn is considered actively streaming.
  • The redundant Working row disappears after visible assistant text begins.
  • The redundant Completed lifecycle label is no longer shown.

Animation choices

  • Fade + lift is the default for existing installations.
  • Word dissolve is the alternative streaming-text animation.
  • The selected animation is stored locally in General settings.
  • Only newly arriving text animates; the whole paragraph does not restart its animation.
  • Markdown-aware tail handling covers first and final chunks without repeatedly fading earlier content.
  • Reduced-motion preferences are respected.

Stop, cancellation, and status behavior

  • Pressing Stop settles the local interface immediately instead of waiting several seconds for the provider interrupt request.
  • The projected streaming assistant message is finalized immediately.
  • Late assistant deltas and late completion events are rejected after interruption.
  • Provider cancellation continues concurrently so the upstream request is still asked to stop.
  • activeTurnId is the authoritative signal that work is currently active.
  • A warm provider session with no active turn renders as ready.
  • Sparky does not send Stop with an invalid or missing turn ID.
  • Environment and provider error banners remain visible, while non-actionable provider-status warnings are suppressed.
  • The separate desktop update-available banner remains available.

Desktop notifications

  • Sparky can send a native desktop notification after an agent turn settles.
  • The notification includes the first seven lines of the response so the result is useful without immediately reopening the app.
  • A completed turn emits one notification rather than repeating the same alert.
  • The notification wiring is shared across Windows, macOS, and Linux builds.

Web search and browser preview

Web search

  • DuckDuckGo HTML results support ordinary URLs, protocol-relative URLs, and redirect-wrapped result URLs.
  • Result URLs are normalized before presentation.
  • Repeated destinations are deduplicated.
  • Changed result delimiters receive updated parsing.
  • User-facing failures use provider-neutral wording.

Browser preview automation

  • Preview bridge subscriptions are more resilient when a preview reconnects.
  • Status fallbacks and retry behavior cover interrupted or incomplete preview operations.
  • Interrupted clicks are cleaned up.
  • Popup URLs receive safer validation and handling.
  • Evaluation return values and recording cleanup are handled more defensively.
  • In-progress preview and tool feedback remains visible while an operation is active.

Application features and distribution services

The desktop features documented above are shared product capabilities. A few release-note items operate outside the installed app because they publish, route, or explain the platform packages.

Verification notes and known boundaries

  • The desktop, local server, and web client package manifests examined while preparing this guide identify version 1.1.2.
  • The Windows executable examined locally reports ProductVersion and FileVersion 1.1.2 and is unsigned; that platform-specific fact does not redefine this as a Windows-only release.
  • An installer wrapper's metadata alone is not treated as proof that every packaged runtime and every platform artifact completed full release certification.
  • The retained image-forwarding work includes strong unit and formatting coverage, but its release notes do not record a live-provider image acceptance test.
  • Provider model lists, context sizes, and reasoning controls remain provider-authoritative and can change independently of the installed app.
  • The retained Linux packaging thread did not record a completed, verified AppImage build. The guide therefore describes the implemented Linux support without claiming a specific local AppImage was release-certified.
  • This page documents the intended contents and behavior of Sparky 1.1.2. It is not a substitute for checksum verification, code-signing verification, or full packaged-runtime certification on every platform.
