Memory

Save the preferences, project conventions, and durable facts Sparky should remember after the current conversation ends.

Available in Sparky 1.1.2: Memory is persistent and manageable. You can create, search, edit, and delete entries in Settings, then let Sparky reuse the relevant context in later conversations.

Memory and session history are different

A session preserves one conversation: its transcript, project binding, and provider continuation state. A memory is a separate durable fact that can be useful in another session. Use the session when the information belongs to the current line of work. Save a memory when you expect Sparky to apply the information again.

InformationBest placeReason
“Continue fixing the failing checkout test.”Current sessionIt depends on the active task and recent tool results.
“Always preserve unrelated working-tree changes.”Global memoryIt is a durable preference that applies across projects.
“Run pnpm test from apps/web before merging.”Project memoryIt is a repeatable convention tied to one workspace.
“The last build failed in auth.test.ts at line 84.”Current sessionIt is temporary diagnostic state that can become stale quickly.

Choose a scope

Global memories

Global memories are available across projects. They work well for communication preferences, review expectations, common tools, and safety rules that should follow you from one workspace to another.

Project memories

Project memories are tied to a workspace. Use them for repository layout, package commands, architectural constraints, naming rules, required checks, or terminology that would be wrong elsewhere.

Keep scope narrow: A project-specific rule saved globally can make future answers less accurate. If a fact names a repository, directory, framework convention, or release process, project scope is usually the clearer choice.

Create and manage memories

  1. Open Settings and select Memory.
  2. Choose whether the entry belongs to every project or only the current workspace.
  3. Write one durable fact or instruction in direct language.
  4. Choose a category and importance level that reflect how the entry should be organized.
  5. Save the entry and confirm that it appears in the Memory list.

Use search to find an existing entry before creating another. Edit a memory when the underlying fact changes. Delete it when it is obsolete or when you no longer want Sparky to reuse it.

Write useful memories

A strong memory is specific, durable, and easy to apply. It states the rule or fact without depending on hidden context from the conversation where it was created.

Clear memory examples
“Use PowerShell commands in this project.”
“The desktop package lives in sparky-desktop/source.”
“Before editing, inspect git status and preserve unrelated changes.”
“User-facing release notes should describe features, not internal performance fixes.”

Avoid saving passwords, API keys, access tokens, short-lived error messages, or guesses that have not been verified. Memory is designed for reusable context, not secret storage or a replacement for project documentation.

How Sparky reuses memory

Sparky resolves available global and project entries, merges duplicate entries by memory ID, and exposes the relevant set to the agent context. Context summaries and recent conversation history remain separate and bounded. A memory does not rewrite the transcript, and a provider-specific continuation record is not exposed as a memory.

When two memories disagree, update or delete the stale entry instead of relying on importance alone to resolve the conflict. Keeping one current source of truth makes the next session more predictable.

Storage, migration, and recovery

Memory storage resolves through the appropriate Sparky data location for Windows, macOS, and Linux. Version 1.1.2 includes migration and recovery handling for earlier memory locations and merges duplicate records that share an ID. This lets existing entries survive a location change without appearing as unrelated copies.

Memory operations expose separate loading, retry, save, update, and delete errors. A failed Memory request is contained so it does not crash the surrounding coding session.

If a memory does not appear

  1. Confirm that you are viewing the intended project and memory scope.
  2. Search for a distinctive phrase from the entry.
  3. Retry after any visible loading or save error.
  4. Open the saved entry and confirm that its latest edit was stored.
  5. If the conversation still uses stale guidance, correct or remove conflicting memories and start a clear follow-up message describing the current rule.

If Memory fails while a task is running, the task should remain usable. Capture the visible error and continue with the required context in the current prompt until Memory is available again.
