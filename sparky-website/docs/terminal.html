Terminal Commands

Run project commands with an explicit working directory, captured output, an exit status, and a visible lifecycle in the task timeline.

How it works

Sparky can run shell commands in the active project's environment. It captures standard output, standard error, and the exit status, then associates that evidence with the task that requested it. Command availability and shell syntax depend on the operating system and project setup.

Running commands

Just tell Sparky what to run. It figures out the right command for your project (npm, cargo, python, go, make, etc.).

Example prompts
"Run the tests"
"Install the dependencies"
"Build the project"
"Run the linter and fix any errors"

Long-running commands

Large test suites and builds can remain active while you inspect the timeline. Use Sparky's Stop control to settle the active turn; if a process owns an interactive terminal, stop it through that terminal's normal interrupt control.

Tip: For dev servers or watchers that run indefinitely, start them in a separate terminal. Sparky works best with commands that have a clear end.

Timeouts

A command can be bounded by the tool or environment that launched it. When it times out, read the output before retrying: the process may have produced useful diagnostics or partial artifacts. Use a focused command, request a suitable finite timeout, or keep an indefinite watcher in a dedicated terminal.

Treat output as evidence

  • A zero exit status is useful but does not prove the produced artifact is correct.
  • A timeout does not prove that no files changed.
  • For builds, inspect the artifact, version, architecture, or checksum required by the task.
  • For tests, record which suite ran and whether skipped or unrelated failures remain.
  • For destructive or publishing commands, make the exact scope explicit before asking Sparky to run them.
